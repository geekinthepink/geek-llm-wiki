# 冲刺契约（Sprint Contract）

## 定义

冲刺契约是 [[generator-evaluator-loop]] 架构中，**生成器（Generator）和评估器（Evaluator）在编写任何代码之前协商达成的协议**。它定义了：

1. 这个冲刺要构建什么（具体实现细节）
2. 如何验证"完成"（可测试的行为标准）
3. 成功的硬性阈值

## 存在原因

产品规格通常有意保持高层级，关注产品上下文和技术设计而非细粒度实现细节。这避免规划器 upfront 指定错误技术细节导致级联错误。但这也带来一个问题：**如何在用户故事和可测试实现之间搭建桥梁？**

冲刺契约就是这个桥梁。它存在于高层规格和底层代码之间，确保：

- 生成器不会过度缩小范围或偏离规格
- 评估器有明确的验证标准
- 两者对"完成"的定义达成一致

## 协商过程

冲刺契约通过**迭代协商**建立：

1. **生成器提议**：生成器提出它要构建什么，以及成功如何被验证
2. **评估器审查**：评估器审查提案，确保生成器在构建正确的东西
3. **迭代调整**：两者反复沟通直到达成一致
4. **契约确立**：写入文件，作为构建的依据

通信通过文件完成——一个 Agent 写入文件，另一个读取并响应，形成可追踪的协商记录。

## 契约内容

一个典型的冲刺契约包含：

- **功能范围**：这个冲刺要实现的具体功能
- **实现细节**：技术栈（React, Vite, FastAPI, SQLite/PostgreSQL）
- **可测试行为**：具体的验证标准
- **通过阈值**：每个维度的硬性评分门槛

### 实例：关卡编辑器冲刺（冲刺 3）

仅一个关卡编辑器冲刺就包含了 **27 条验证标准**，例如：

| 契约标准 | 评估结果 |
|---|---|
| 矩形填充工具允许点击拖拽填充矩形区域 | 失败——工具仅在拖拽起止点放置图块 |
| 用户可以选择和删除放置的实体生成点 | 失败——条件逻辑有误 |
| 用户可以通过 API 重新排序动画帧 | 失败——路由定义顺序问题导致 422 错误 |

## 与生成器-评估器循环的关系

冲刺契约是 [[generator-evaluator-loop]] 中的关键协调机制：

```
产品规格（高层）
    │
    ▼
┌──────────────────────────────┐
│    冲刺契约协商               │
│  生成器 ←──→ 评估器           │
│  （定义"完成"标准）           │
└──────────────────────────────┘
    │
    ▼
生成器构建（基于契约）
    │
    ▼
评估器 QA 验证（对照契约）
    │
    ├── 通过 → 下一个冲刺
    └── 失败 → 详细反馈 → 生成器修复
```

## 文件化通信

契约以文件形式存在，保持：

- **可追溯性**：协商过程有记录
- **可验证性**：标准明确可测试
- **可交接性**：Agent 之间通过文件传递上下文

## 演化：移除冲刺结构

在后续迭代中，随着 Opus 4.6 模型能力提升，Anthropic 尝试完全移除冲刺结构：

- 生成器不再逐个功能工作，而是连续构建
- 评估器从每冲刺评分改为运行结束时一次性 QA
- **关键发现**：当模型能力提升到可以独立可靠完成某些任务时，冲刺契约变成不必要的开销；但对于仍处于模型能力边缘的任务部分，契约机制仍然提供价值

## 设计原则

1. **先定义完成，再开始编码**——避免生成器盲目构建
2. **契约必须可测试**——每个标准都要能被评估器验证
3. **保持高层规格不变**——契约桥接但不改变产品愿景
4. **迭代协商**——生成器和评估器必须达成一致，而非单方面决定
