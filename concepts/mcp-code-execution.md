# MCP 代码执行模式

## 定义

MCP 代码执行模式是 Anthropic 在《Code execution with MCP: Building more efficient agents》中提出的一种 Agent 工具使用架构：不要把所有 MCP 工具直接暴露给模型做逐步工具调用，而是把 [[model-context-protocol]] server 暴露成代码执行环境里的 API，让 Agent 写代码按需调用工具、过滤数据、组合流程和保存状态。

它解决的是 MCP 规模化后的上下文效率问题：当 Agent 连接大量工具和 server 时，工具定义、参数 schema 和中间工具结果会占用大量上下文窗口，导致成本、延迟和推理质量下降。

## 核心机制

| 维度 | 直接工具调用 | MCP 代码执行模式 |
|---|---|---|
| 工具暴露 | 所有工具定义预先进入模型上下文 | 按需在代码环境中导入或发现 |
| 中间数据 | 每一步结果进入上下文 | 大结果留在执行环境中处理 |
| 控制流 | 模型逐步决定下一次调用 | 代码处理循环、分页、过滤、重试 |
| 状态 | 主要依赖对话上下文 | 可写入文件、缓存、函数、skill |
| 安全要求 | 较简单 | 需要沙箱、资源限制和监控 |

## 为什么有效

1. **渐进式披露**：模型先看到少量入口和任务目标，需要具体工具时再在执行环境中查询或导入，避免“工具文档洪水”。
2. **上下文节省**：大文本、大表格、批量记录可以在代码里过滤或转存，只把最终摘要返回模型。
3. **工具组合增强**：代码天然支持循环、条件分支、重试、批处理和局部状态，比逐个工具调用更适合复杂工作流。
4. **隐私边界更清晰**：敏感原始数据可停留在执行环境，只返回脱敏结果或聚合指标。
5. **能力可复用**：常用脚本、函数和 `SKILL.md` 可沉淀为高层能力，这与 [[hermes-skill-implementation]] 的 skill 机制相呼应。

## 适用场景

- Agent 同时连接大量 MCP server 或上百个工具。
- 任务需要跨系统搬运大文本、大文件或批量记录。
- 任务需要复杂控制流：循环、分页、重试、过滤、聚合。
- 希望把工具组合封装成可复用脚本或 skill。
- 希望减少敏感数据进入模型上下文。

## 不适用或需谨慎的场景

- 只需要调用少量简单工具。
- 执行环境无法提供可靠沙箱。
- 权限模型不清晰，Agent 生成代码可能造成越权操作。
- 任务需要模型逐字理解所有中间数据，而不是简单搬运或聚合。

## 与现有 Agent 工程的关系

这个模式延续了 [[anthropic-agent-harness]] 和 [[harness-engineering]] 的共同方向：把大模型放在“规划、判断、生成策略”的位置，把确定性执行、环境管理和可复用程序性知识交给外部系统。MCP 提供连接协议，代码执行提供控制流和状态，skill 或文档提供可复用经验。

## 开放问题

- MCP client 应该如何设计“工具发现 API”，才能让 Agent 高效地按需找到正确工具？
- 代码执行沙箱的默认权限边界应该多窄？
- 如何在审计日志中同时保留代码执行透明度和敏感数据最小暴露？
- 哪些工具应该直接暴露给模型，哪些应该只作为代码 API 暴露？
