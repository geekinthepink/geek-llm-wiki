# Claude Code Dynamic Workflows（动态工作流）

## 概述

> **作者：** Thariq Shihipar (@trq212)，Anthropic
> **日期：** 2026-06-03
> **来源：** [X 帖子](https://x.com/trq212/status/2061907337154367865) | Claude Blog

Anthropic 为 [[claude-code]] 推出了动态工作流（Dynamic Workflows）功能。Claude 现在能够即时自行编写 harness（执行框架），针对手头的具体任务量身定制。

默认的 [[anthropic-agent-harness]] 是为编码任务设计的，但由于许多任务在结构上类似于编码任务，它也能胜任很多其他类型的工作。然而，某些特定类别的任务——如研究（Research）、安全分析、[[parallel-agent-teams]] 或代码审查——需要在 Claude Code 之上构建定制 harness 才能达到最佳性能。

动态工作流允许你动态创建 harness，使 Claude 能够原生地在 Claude Code 内部解决这些问题乃至更多。你还可以与他人分享和复用这些工作流。

> **注意：** 最佳实践仍在发展中！动态工作流通常消耗更多 token，因此需要仔细考虑何时以及如何使用它们。

## 示例 Prompt

在深入技术细节之前，以下是一些示例 prompt，帮助你思考工作流的可能性：

- "这个测试大约每 50 次运行中会失败 1 次。设置一个工作流来复现它，形成假设并进行对抗性测试，在 worktree 中运行，/goal 模式下持续直到某个假设成立。"
- "使用工作流，浏览我最近 50 次会话，挖掘我反复犯的纠正错误，将重复出现的内容转化为 CLAUDE.md 规则。"
- "使用工作流深入分析 Slack 上 #incidents 频道过去六个月的消息，找到那些没人提交工单的反复出现的根本原因。"
- "拿我的商业计划书，运行一个工作流，让不同的 Agent 分别从投资者、客户和竞争对手的角度进行批判性分析。"
- "这里有 80 份简历的文件夹，使用工作流为后端岗位进行排名，并对前十名进行复核。使用 AskUserQuestion 工具对我进行面试以获取评分标准。"
- "我需要为这个 CLI 工具起个名字。使用工作流头脑风暴大量选项，然后运行锦标赛选出前 3 名。"
- "使用工作流将我们的 User 模型在所有地方重命名为 Account。"
- "浏览我的博客文章草稿，使用工作流验证每一项技术声明是否与代码库一致，我不想发布任何错误内容。"

## 动态工作流的工作原理

动态工作流通过执行一个 JavaScript 文件来运行，该文件包含几个特殊函数，用于生成和协调子 Agent（subagent）：

工作流还包含标准 JavaScript 函数（如 JSON、Math 和 Array），用于辅助数据处理。

特别值得了解的是，动态工作流可以决定 Agent 使用哪个模型，以及子 Agent 是否在独立的 worktree 中运行，这使得 Claude 能够自行选择所需的智能水平和隔离程度。

如果工作流被中断（例如用户操作或退出终端），恢复会话时工作流能够从断点处继续。

## 为什么需要动态工作流

当你让默认的 Claude Code harness 执行任务时，它需要在同一个上下文窗口中同时进行规划和执行。对于许多编码任务来说，这种方式非常高效，但在长时间运行、大规模并行和/或高度结构化的对抗性任务中，有时会失效。

这是因为 Claude 在单个上下文窗口中处理复杂任务的时间越长，就越容易受到以下几种特定失败模式的影响：

- **Agentic laziness（Agent 惰性）：** 当 Claude 在完成一个特别复杂的多部分任务前提前停止，并在取得部分进展后就宣布任务完成——例如在安全审查中只处理了 50 项中的 20 项。
- **Self-preferential bias（自我偏好偏差）：** Claude 倾向于偏爱自己的结果或发现，尤其是在被要求根据评分标准进行验证或评判时。
- **Goal drift（目标漂移）：** 在多次交互后，尤其在压缩（compaction）之后，逐渐偏离原始目标。每次摘要步骤都是有损的，边缘情况需求或"不要做 X"之类的约束可能会丢失。

创建工作流有助于通过编排各自拥有独立上下文窗口和专注、隔离目标的多个 Claude 实例来对抗这些问题。

## 动态工作流 vs 静态工作流

你可能之前使用过 Claude Agent SDK 或 `claude -p` 创建过静态工作流，将多个 Claude Code 实例协调在一起。

但由于静态工作流需要适用于所有边界情况，它们通常更加通用。借助 Claude Opus 4.8 和动态工作流，Claude 现在足够智能，能够为你的具体用例编写量身定制的定制 harness。

## 使用动态工作流的常用模式

你可以通过直接让 Claude 创建工作流，或使用触发词 "ultracode" 来确保 Claude Code 创建工作流，即可开始使用动态工作流。

但建立对动态工作流如何运作的心理模型，将帮助你理解何时使用它们以及如何通过 prompt 引导 Claude。

Claude 在构建工作流时可能会使用和组合以下几种常见模式：

### 1. Classify-and-act（分类-行动）

使用分类器 Agent 决定任务类型，然后根据任务路由到不同的 Agent 或行为。或者在末尾使用分类器来确定输出。

### 2. Fan-out-and-synthesize（扇出-综合）

将一个任务拆分为多个更小的步骤，在每个步骤上运行一个 Agent，然后综合这些结果。这在存在大量小步骤时特别有用，或者当每个步骤受益于自己干净的上下文窗口以避免相互干扰或交叉污染时。**综合步骤是一个屏障（barrier）**——它等待所有扇出 Agent 完成后，再将它们的结构化输出合并为一个结果。

这种模式与 [[generator-evaluator-loop]] 中的并行生成思想类似。

### 3. Adversarial verification（对抗性验证）

对于每个生成的 Agent，运行一个独立的生成 Agent 来根据评分标准或准则对抗性地验证其输出。

### 4. Generate-and-filter（生成-过滤）

围绕某个主题生成大量想法，然后根据评分标准或验证进行过滤，去除重复项，只返回经过测试的高质量想法。

### 5. Tournament（锦标赛）

不是划分工作，而是让 Agent 在同一任务上竞争。生成 N 个 Agent，每个 Agent 使用不同的方法尝试同一任务。然后通过裁判 Agent 以两两对比的方式评判结果，直到产生胜出者。

### 6. Loop until done（循环直到完成）

对于工作量未知的任务，循环生成 Agent 直到满足停止条件（没有新发现，或日志中没有更多错误），而不是固定次数的遍历。

## 使用场景

创造性地思考何时以及如何让 Claude Code 创建动态工作流。我发现工作流有时甚至在非技术工作中更有用。

### 迁移和重构（Migrations and Refactors）

Bun 使用工作流从 Zig 重写为 Rust。你可以在 Jarred 的 X 帖子中阅读更多细节。

关键在于将任务分解为需要操作的一系列步骤——例如调用点（callsites）、失败的测试、模块等。为每个修复派生一个子 Agent 在 worktree 中进行修复，然后让另一个 Agent 进行对抗性审查，最后合并。考虑告诉 Agent 不要使用资源密集型的命令，这样你就可以最大化并行化而不会耗尽机器资源。

### 深度研究（Deep Research）

我们在 Claude Code 内发布了一个深度研究技能（/deep-research），它使用了动态工作流。具体来说，它对网络搜索进行扇出（fan-out）、获取来源、对抗性地验证其声明，然后综合出一份带有引用的报告。

但这类研究不仅限于网络搜索。例如，让 Claude 从 Slack 上下文中编译状态报告，或通过深入探索代码库来研究某个功能的工作原理。

### 深度验证（Deep Verification）

反过来，如果你有一份报告需要检查并溯源每一个事实声明，你可能希望生成一个工作流：一个 Agent 识别所有事实声明，然后为每个声明派生一个子 Agent 进行详细检查。你还可以让一个验证 Agent 检查来源子 Agent，确保其来源质量可靠。

### 排序（Sorting）

你可能有一个项目列表，需要根据某些定性指标进行排序，而你认为 Claude Code 擅长评估这些指标——例如：按 bug 严重程度排序的工单。但如果你在一个 prompt 中尝试对 1000+ 行进行排序，质量会下降且无法放入上下文。此时应运行锦标赛、两两比较 Agent 流水线（比较判断比绝对评分更可靠），或并行分桶排名再合并。每次比较都是一个独立的 Agent，因此确定性循环维护着对阵表，只有运行顺序保留在上下文中。

### 记忆和规则遵循（Memory and Rule Adherence）

如果你发现 Claude 对某些特定规则存在遗漏或困难——即使已写入 CLAUDE.md——可以创建一个工作流，其中规则列表必须由验证 Agent 逐一检查——每条规则一个验证者。创建一个怀疑论者角色（skeptic persona）子 Agent 来审查这些规则，确保它们合理，有助于避免过多的误报。

反向操作同样有效：挖掘你最近的会话和代码审查意见，找出你反复做的纠正，用并行 Agent 进行聚类，对抗性地验证每个候选规则（这条规则是否真的能防止一个实际的错误？），然后将幸存的规则提炼回 CLAUDE.md。

### 根本原因调查（Root-cause Investigation）

调试最有效的方式是提出多个独立假设并逐一测试。但如果只使用一个上下文窗口，Claude 可能会陷入自我偏好偏差。

工作流可以通过结构性地生成 Agent 从互不重叠的证据中生成假设来防止这一点。例如，分别为日志、文件和数据设置独立的 Agent。然后每个假设可以面对一组验证者和反驳者。

这不仅适用于代码。工作流还可用于销售（为什么三月份销售额下降了？）、数据工程（为什么这个管道失败了？）或任何事后复盘（post-mortem）场景。

### 大规模分诊（Triaging at Scale）

每个团队都有一个支持队列、bug 报告或其他某种人类无法完全处理的积压工作。

分诊工作流对每个项目进行分类、与已跟踪的内容去重，然后采取行动。这可能意味着尝试修复或升级给人类用户。

分诊工作流的一个有用模式是**隔离（quarantine）**：这包括禁止读取不受信任的公开内容的 Agent 执行高权限操作，这些操作改由负责根据信息采取行动的 Agent 来执行。

将分诊工作流与 /loop 搭配使用，可以让 Claude 持续执行此操作。

### 探索和品味（Exploration and Taste）

当探索解决方案的不同方法时，尤其是基于品味的方法——如设计或命名——工作流会很有帮助，因为它们受益于评分标准。

尝试让 Claude 探索大量解决方案，并给审查 Agent 一个关于好解决方案长什么样子的评分标准。当审查 Agent 认为已满足标准时，任务即完成。解决方案也可以根据评分标准通过锦标赛进行排序或选择。

### 评估（Evals）

你可以通过在 worktree 中派生独立的 Agent 来运行特定任务的轻量级评估，然后派生比较 Agent 根据评分标准对特定输出进行比较和评分。例如，针对特定标准评估和细化你创建的技能。

### 模型和智能路由（Model and Intelligence Routing）

创建一个针对你的任务调优的分类器 Agent，来决定使用哪个模型。当你的任务涉及大量工具调用时，这很有帮助——在执行前进行研究可以识别最适合该任务的模型。

例如，"解释 auth 模块如何工作"这一任务的最佳模型取决于 auth 模块中有多少文件以及代码库的结构。分类器 Agent 可以进行这项研究，然后根据任务的预期复杂度路由到 Sonnet 或 Opus。

## 何时不使用动态工作流

工作流是新的功能。虽然在许多用例中它会产生显著的效果，但并非每个任务都需要它们，而且它们最终可能会消耗显著更多的 token。

最好创造性地使用工作流，以你之前未曾尝试的方式推动 Claude Code。对于常规编码任务，请问自己：它真的需要更多计算力吗？例如，大多数传统编码任务不需要 5 个评审员的审查团。

## 构建动态工作流的技巧

### Prompt 设计

详细的 prompt 设计，使用我们上面描述的具体技术，可以为动态工作流创造最佳结果。

工作流不仅适用于大型任务。你可以 prompt 模型使用"快速工作流"（quick workflow）。例如，你可以对一个假设创建快速的对抗性审查。

### 与 /goal 和 /loop 结合使用

当使用可重复的工作流时——例如分诊、研究或验证——将它们与 /loop 搭配以定期运行，并与 /goal 搭配以设置硬性完成要求。

### Token 使用预算

你可以为动态工作流设置明确的 token 使用预算，以限制任务消耗的 token 数量。你可以用类似这样的预算进行 prompt："使用 10k token"，这将设置上限。

### 保存和分享动态工作流

你可以在工作流菜单中按 "s" 来保存工作流。你可以将它们提交到 `~/.claude/workflows` 或通过 skill 分发。

要通过 skill 分享，将你的 JavaScript 工作流文件放在 skill 的文件夹中，并在 SKILL.md 中引用它们。为了更大的灵活性，你可能希望 prompt Claude 将 skill 中的工作流视为模板，而不是需要逐字运行的脚本。

## 全新世界

工作流是扩展 Claude Code 的一种有用新方式。我鼓励你将其视为一个起点——如何最佳使用它们仍有许多值得发现。让我们知道你发现了什么。
