# 生成器-评估器循环（Generator-Evaluator Loop）

## 定义

生成器-评估器循环是一种受**生成对抗网络（GAN）**启发的多 Agent 架构模式，其中两个独立的 Agent 角色形成反馈闭环：

- **生成器（Generator）**：负责执行实际工作（如编写代码、创建设计）
- **评估器（Evaluator）**：负责对生成器的产出进行独立评判和批评

两者通过迭代循环相互驱动——生成器产出工作，评估器给出评分和详细反馈，生成器根据反馈改进——推动输出质量不断提升。

## 核心动机

### 自我评估失效

LLM 在评估自己产出的工作时存在系统性偏差：倾向于自信地赞美自己的作品，即使质量平庸。这在主观任务（如前端设计）中尤为严重，因为没有二进制测试可依赖。

将**执行工作的 Agent 和评判工作的 Agent 分离**是解决此问题的关键杠杆。虽然评估器本身也是 LLM，也会倾向宽容，但**调整一个独立评估器使其变得怀疑，远比让生成器批判自己的工作容易得多**。

### 上下文焦虑与重置

长任务中模型随上下文窗口填满而失去连贯性，甚至出现"上下文焦虑"（过早结束工作）。通过结构化交接在生成器-评估器循环中传递状态，配合上下文重置，可以保持 Agent 在长期任务中的专注。

## 前端设计中的四维度评分

在 Anthropic 的前端设计实验中，评估器使用**四个评分维度**对生成器的产出进行评判：

| 维度 | 描述 | 权重 |
|---|---|---|
| **设计质量**（Design Quality） | 设计是否是连贯整体而非部件拼凑？颜色、排版、布局、图像等是否创造独特氛围和身份？ | 高 |
| **原创性**（Originality） | 是否有定制决策证据，还是模板布局、库默认值和 AI 生成模式？是否惩罚"AI 垃圾"模式？ | 高 |
| **工艺**（Craft） | 技术执行：排版层次、间距一致性、色彩和谐、对比度比率。能力检查而非创造力检查。 | 低 |
| **功能性**（Functionality） | 独立于美学的可用性。用户能否理解界面、找到主要操作、完成任务？ | 低 |

**设计质量和原创性被赋予更高权重**，因为 Claude 默认在工艺和功能性上得分已经不错，但在设计和原创性上产出往往平淡。

## Playwright MCP 交互评估

评估器不是对静态截图评分，而是通过 **Playwright MCP** 与运行中的页面进行**实时交互**：

- 自主导航页面
- 截图并仔细研究实现
- 点击、滚动、测试交互
- 对每个维度评分并撰写详细评论

这种方式让评估更接近真实用户体验，但代价是每个循环都花费真实的墙上时钟时间，完整运行可达数小时。

## 迭代行为模式

每次生成运行 **5-15 次迭代**，生成器在每次评估后做出战略决策：

- **分数趋势良好** → 优化当前方向
- **方法不奏效** → 完全转向不同的美学/实现风格

迭代中观察到的模式：
- 评估分数逐步提高最终趋于平稳
- 有些生成逐步精炼，有些发生剧烈转向
- 实现复杂度倾向于在多轮中增加
- 即使首次迭代也优于无提示词基线
- 标准的措辞直接塑造输出特征（如"博物馆级别"推动特定视觉收敛）

## 在全栈开发中的扩展

生成器-评估器循环自然映射到软件开发生命周期，代码审查和 QA 充当与设计评估器相同的结构角色。在全栈版本中：

- 评估器测试 UI 功能、API 端点、数据库状态
- 每个冲刺有硬性阈值，低于阈值即失败
- 评估器发现可直接行动的 bug 报告

## 评估器调优

开箱即用的 Claude 是糟糕的 QA Agent——会识别真正问题然后说服自己认为不重要。调优循环：

1. 阅读评估器日志
2. 找出判断与人类不一致的例子
3. 更新评估器提示词
4. 多轮迭代直到评分合理

## 与模型能力的关系

评估器是否值得使用取决于任务相对于模型能力的定位：

- 任务接近模型能力边缘 → 评估器提供显著提升
- 任务在模型可靠能力范围内 → 评估器变成不必要的开销

随着模型改进，这个边界向外移动，但**评估器对处于边界的任务始终有价值**。
