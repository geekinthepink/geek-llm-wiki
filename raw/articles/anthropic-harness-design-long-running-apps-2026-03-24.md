# Harness Design for Long-Running Application Development（长期应用开发的 Harness 设计）

> **作者**：Prithvi Rajasekaran（Anthropic Labs 团队成员）
> **发布日期**：2026 年 3 月 24 日

---

## 引言

在过去的几个月里，我一直致力于两个相互关联的问题：让 Claude 产出高质量的前端设计，以及让它在没有人工干预的情况下构建完整的应用程序。这项工作源于我们早期在前端设计技能和长期运行编码 Agent harness 上的努力——我的同事们和我通过提示词工程和 harness 设计将 Claude 的性能提升到远超基线水平，但两者最终都触及了天花板。

为了突破瓶颈，我探索了新颖的 AI 工程方法，这些方法在两个截然不同的领域中都能奏效：一个由主观品味定义，另一个由可验证的正确性和可用性定义。受**生成对抗网络（GAN）**的启发，我设计了一个多 Agent 架构，包含生成器（generator）和评估器（evaluator）Agent。构建一个能够可靠且有品味地评判输出的评估器，意味着首先需要开发一套标准，将"这个设计好不好？"等主观判断转化为具体、可评分的维度。

随后，我将这些技术应用于长期自主编码，从早期的 harness 工作中继承了两条经验：将构建任务分解为可处理的小块，以及使用结构化产物在会话之间传递上下文。最终结果是一个**三 Agent 架构——规划器（planner）、生成器（generator）和评估器（evaluator）**——能够在数小时的自主编码会话中产出丰富的全栈应用程序。

## 为什么朴素实现会失败

我们之前已经展示过，harness 设计对长期运行 Agent 编码的有效性有着重大影响。在早期的一个实验中，我们使用初始化 Agent 将产品规格分解为任务列表，编码 Agent 逐个功能实现，然后在会话之间传递产物以携带上下文。开发者社区也收敛于类似的见解，比如使用钩子或脚本让 Agent 进入持续迭代循环的"Ralph Wiggum"方法。

但仍有一些问题持续存在。对于更复杂的任务，Agent 在运行一段时间后仍然容易偏离轨道。在分解这个问题时，我们观察到 Agent 执行此类任务时的两种常见失败模式。

**第一种**：模型在长任务上随着上下文窗口被填满而失去连贯性（参见我们关于上下文工程的文章）。一些模型还会表现出"上下文焦虑"——当接近它们认为的上下文限制时，会过早地结束工作。**上下文重置**——完全清除上下文窗口并启动一个全新的 Agent，结合结构化交接来传递上一个 Agent 的状态和后续步骤——可以同时解决这两个问题。

这与压缩（compaction）不同，压缩是在原位置总结对话的早期部分，让同一个 Agent 在缩短的历史记录上继续工作。虽然压缩保留了连续性，但它没有给 Agent 一个干净的状态，因此上下文焦虑仍然可能存在。重置提供了干净的状态，代价是交接产物必须包含足够的状态，让下一个 Agent 能够干净地接手工作。在我们早期的测试中，我们发现 Claude Sonnet 4.5 表现出强烈的上下文焦虑，仅靠压缩不足以实现强大的长任务性能，因此上下文重置成为 harness 设计的关键。这解决了核心问题，但也给每次 harness 运行增加了编排复杂性、Token 开销和延迟。

**第二种**是我们之前没有解决过的：自我评估。当被要求评估自己完成的工作时，Agent 往往会自信地赞美这些作品——即使在人类观察者看来质量明显平庸。这个问题在主观任务（如设计）中尤为突出，因为没有等同于可验证软件测试的二元检查。一个布局是否精致或平庸是一种主观判断，而 Agent 在评判自己工作时总是倾向于正面。

然而，即使在有可验证结果的任务上，Agent 有时也会表现出糟糕的判断力，影响它们完成任务的表现。将执行工作的 Agent 和评判工作的 Agent 分开，是解决这个问题的强大杠杆。这种分离本身并不会立即消除宽松性——评估器仍然是一个对 LLM 生成输出倾向于慷慨的 LLM。但调整一个独立的评估器使其变得怀疑，远比让生成器批判自己的工作要容易得多，而且一旦存在这种外部反馈，生成器就有了可以迭代改进的具体目标。

## 前端设计：让主观质量可评分

我首先在前端设计上做实验，因为自我评估问题在这里最为明显。在没有任何干预的情况下，Claude 通常倾向于安全、可预测的布局，技术上可用但视觉上平庸。

两个洞察塑造了我为前端设计构建的 harness。**第一**，虽然美学不能完全简化为分数——个人品味永远会有差异——但它们可以通过编码设计原则和偏好的评分标准来改善。"这个设计美吗？"很难一致地回答，但"它是否遵循了我们对于好设计的原则？"给了 Claude 一个具体的评分参照。**第二**，通过将前端生成和前端评分分离，我们可以创建一个反馈循环，推动生成器向更强的输出发展。

基于此，我为生成器和评估器 Agent 的提示词编写了**四个评分标准**：

1. **设计质量（Design Quality）**：设计感觉是一个连贯的整体，而不是部件的拼凑？这意味着颜色、排版、布局、图像和其他细节结合起来创造独特的氛围和身份。
2. **原创性（Originality）**：是否有定制决策的证据，还是模板布局、库默认值和 AI 生成的模式？人类设计师应该能认出有意识的创意选择。未修改的库存组件——或 AI 生成的明显痕迹（如白色卡片上的紫色渐变）——在这里会失败。
3. **工艺（Craft）——技术执行**：排版层次、间距一致性、色彩和谐、对比度比率。这是能力检查而非创造力检查。大多数合理的实现默认情况下都能过关；失败意味着基础功 broken。
4. **功能性（Functionality）**：独立于美学的可用性。用户能否理解界面做什么、找到主要操作并在不猜测的情况下完成任务？

我**强调设计质量和原创性，高于工艺和功能性**。Claude 在工艺和功能性上默认得分就不错，因为所需的技术能力对模型来说是自然的。但在设计和原创性方面，Claude 产出的输出充其量是平淡的。标准明确惩罚高度通用的"AI 垃圾"模式，通过更重地加权设计和原创性，推动模型进行更多的美学冒险。

我使用带有详细分数分解的少样本示例校准了评估器。这确保评估器的判断与我的偏好一致，并减少了迭代间的分数漂移。

我在 Claude Agent SDK 上构建了这个循环，保持了编排的简洁。生成器 Agent 首先基于用户提示创建 HTML/CSS/JS 前端。我给了评估器 **Playwright MCP**，让它可以直接与实时页面交互，然后对每个标准评分并撰写详细评论。在实践中，评估器会自行导航页面，截图并仔细研究实现，然后产出评估。该反馈流回生成器，作为下一次迭代的输入。

我每次生成运行 **5 到 15 次迭代**，每次迭代通常推动生成器向更独特的方向发展，因为它响应评估器的批评。因为评估器是在主动导航页面而非对静态截图评分，每个循环都花费了真实的墙上时钟时间。完整运行长达四小时。我还指示生成器在每次评估后做出战略决策：如果分数趋势良好，则优化当前方向；如果方法不奏效，则完全转向不同的美学风格。

在多次运行中，评估器的评分在迭代中不断提高，最终趋于平稳，仍有提升空间。一些生成逐步精炼。另一些在迭代之间发生了剧烈的美学转向。

标准的措辞以我没有完全预料到的方式引导了生成器。包含"最好的设计是博物馆级别"这样的短语推动设计向特定的视觉收敛，表明与标准相关的提示词直接塑造了输出的特征。

虽然分数总体上在迭代中提高，但模式并不总是干净的线性。后来的实现在整体上往往更好，但我经常发现我更喜欢中间的迭代而非最后一个。实现复杂度也倾向于在多轮中增加，生成器响应评估器的反馈而采取更雄心勃勃的解决方案。即使在第一次迭代中，输出也明显优于没有任何提示词的基线，这表明标准本身及其相关语言在评估器反馈导致进一步精炼之前，就已经将模型从通用默认值中引导出来。

在一个值得注意的例子中，我提示模型为一个荷兰艺术博物馆创建网站。到第九次迭代时，它产出了一个干净的暗色主题虚构博物馆着陆页。页面视觉精致，但基本符合我的预期。然后在第十个循环中，它完全抛弃了这个方法，将网站重新想象为一个空间体验：一个用 CSS 透视渲染的棋盘格地板的 3D 房间，艺术品以自由形式挂在墙上，基于门廊的画廊房间导航而非滚动或点击。这是一种我从未在单次生成中见过的创意飞跃。

## 扩展到全栈编码

带着这些发现，我将这个受 GAN 启发的模式应用于全栈开发。生成器-评估器循环自然地映射到软件开发生命周期，其中代码审查和 QA 充当与设计评估器相同的结构角色。

### 架构

在我们早期的长期运行 harness 中，我们通过初始化 Agent、逐个功能工作的编码 Agent 以及会话间的上下文重置，解决了连贯的多会话编码问题。上下文重置是关键解锁：harness 使用了 Sonnet 4.5，它表现出前面提到的"上下文焦虑"倾向。创建一个能跨上下文重置良好工作的 harness，是保持模型专注于任务的关键。Opus 4.5 在很大程度上自行消除了这种行为，因此我能够完全从这个 harness 中删除上下文重置。Agent 在整个构建过程中作为一次连续会话运行，由 Claude Agent SDK 的自动压缩功能处理上下文增长。

对于这项工作，我在原始 harness 的基础上构建了一个**三 Agent 系统**，每个 Agent 解决我在先前运行中观察到的特定空白。系统包含以下 Agent 角色：

**规划器（Planner）**：我们之前的长期运行 harness 要求用户 upfront 提供详细规格。我想自动化这一步，因此创建了一个规划器 Agent，它接受简单的 1-4 句话提示，并将其扩展为完整的产品规格。我提示它对范围保持雄心勃勃，并专注于产品上下文和高层技术设计，而非详细的技术实现。这种强调是因为担心如果规划器 upfront 指定细粒度的技术细节并出错，规格中的错误会级联到下游实现中。更明智的做法是约束 Agent 要产出的交付物，让它们在工作时自己找出路径。我还要求规划器寻找机会将 AI 功能编织到产品规格中。

**生成器（Generator）**：早期 harness 中逐个功能的方法在范围管理方面效果很好。我在这里应用了类似的模型，指示生成器以冲刺（sprint）方式工作，从规格中一次挑选一个功能。每个冲刺使用 React、Vite、FastAPI 和 SQLite（后来是 PostgreSQL）技术栈实现应用，生成器被指示在每个冲刺结束时自我评估工作，然后交接给 QA。它还使用 git 进行版本控制。

**评估器（Evaluator）**：早期 harness 中的应用程序看起来令人印象深刻，但实际使用时仍有真正的 bug。为了捕获这些，评估器使用 **Playwright MCP** 像用户一样点击运行中的应用程序，测试 UI 功能、API 端点和数据库状态。然后根据它发现的 bug 和一套标准（基于前端实验建模，这里适配为覆盖产品深度、功能性、视觉设计和代码质量）对每个冲刺进行评分。每个标准都有一个硬性阈值，如果任何一个低于阈值，冲刺即失败，生成器获得关于出错的详细反馈。

在每个冲刺之前，**生成器和评估器协商一个冲刺契约（sprint contract）**：在编写任何代码之前，就这一小块工作的"完成"标准达成一致。之所以存在这一步，是因为产品规格有意保持高层级，而我想要一个步骤来弥合用户故事和可测试实现之间的鸿沟。生成器提出它要构建什么以及如何验证成功，评估器审查该提案以确保生成器在构建正确的东西。两者迭代直到达成一致。

通信通过文件处理：一个 Agent 写入文件，另一个 Agent 读取它并在该文件内或以新文件响应，前一个 Agent 再依次读取。然后生成器基于商定好的契约进行构建，再将工作交接给 QA。这使得工作忠于规格，又不会过早过度指定实现细节。

### 运行 Harness

对于这个 harness 的第一个版本，我使用了 Claude Opus 4.5，针对完整 harness 和单 Agent 系统运行用户提示以进行比较。我使用 Opus 4.5 是因为在开始这些实验时这是我们最好的编码模型。

我写了以下提示来生成一个复古视频游戏制作器：

> *创建一个 2D 复古游戏制作器，功能包括关卡编辑器、精灵编辑器、实体行为和可玩的测试模式。*

| Harness 类型 | 运行时长 | 成本 |
|---|---|---|
| 单 Agent（Solo） | 20 分钟 | $9 |
| 完整 Harness | 6 小时 | $200 |

Harness 的成本超过了 20 倍，但输出质量的差异一目了然。

单 Agent 的输出初看符合预期，但点击后问题开始出现：布局浪费空间，固定高度的面板让大部分视口空置。工作流僵化。更关键的是，实际游戏是 broken 的——实体出现在屏幕上但对输入没有响应。深入代码发现实体定义和游戏运行时之间的连接是 broken 的。

而 Harness 运行从同样的单句提示开始，但规划器步骤将其扩展为一个**跨越十个冲刺的 16 功能规格**。它远超单 Agent 运行的尝试范围。除了核心编辑器和播放模式外，规格还要求精灵动画系统、行为模板、音效和音乐、AI 辅助精灵生成器和关卡设计器，以及带可分享链接的游戏导出。对于每个冲刺，生成器和评估器协商了一个契约，定义了冲刺的具体实现细节和用于验证完成的可测试行为。

Harness 产出的应用立即显示出更多的打磨和流畅度。画布使用了完整的视口，面板尺寸合理，界面有一致的视觉身份，追踪了规格中的设计方向。sprite 编辑器更丰富、功能更完善，拥有更干净的工具调色板、更好的颜色选择器和更易用的缩放控制。

最大的区别在播放模式。我实际上能够移动我的实体并玩游戏。核心功能奏效了——这是单 Agent 运行没有做到的。

通过阅读日志，可以清楚地看到评估器让实现与规格保持一致。每个冲刺，它都遍历冲刺契约的测试标准，通过 Playwright 演练运行中的应用，对任何偏离预期行为的内容提交 bug。契约非常细粒度——仅冲刺 3 就有 27 条覆盖关卡编辑器的标准——评估器的发现足够具体，可以直接行动而无需额外调查。

| 契约标准 | 评估器发现 |
|---|---|
| 矩形填充工具允许点击拖拽填充矩形区域 | 失败——工具仅在拖拽起止点放置图块，而非填充区域。fillRectangle 函数存在但未被正确触发。 |
| 用户可以选择和删除放置的实体生成点 | 失败——删除键处理器要求 selection 和 selectedEntityId 都设置，但点击实体仅设置 selectedEntityId。 |
| 用户可以通过 API 重新排序动画帧 | 失败——PUT /frames/reorder 路由定义在 /{frame_id} 路由之后。FastAPI 将 'reorder' 匹配为 frame_id 整数并返回 422 错误。 |

让评估器达到这个水平需要大量工作。开箱即用的 Claude 是一个糟糕的 QA Agent。在早期运行中，我看到它识别出真正的问题，然后说服自己认为这些不是什么大事并批准工作。它还倾向于表面化测试而非探测边缘情况。调优循环是阅读评估器的日志，找出其判断与我不同的例子，然后更新 QA 提示词来解决这些问题。经过几轮这样的开发循环，评估器才以我认为合理的方式评分。

## 迭代优化 Harness

第一批 harness 结果令人鼓舞，但也臃肿、缓慢且昂贵。合乎逻辑的下一步是找到简化 harness 的方法而不降低其性能。这既是常识，也反映了一个更普遍的原则：harness 中的每个组件都编码了关于模型不能独自做什么的假设，而这些假设值得压力测试——因为它们可能不正确，而且随着模型改进会迅速过时。

在第一批简化尝试中，我激进地削减了 harness 并尝试了一些创意新想法，但无法复现原始性能。基于那次经验，我转向更系统的方法，一次移除一个组件并审查其对最终结果的影响。

在这些迭代周期中，我们还发布了 **Opus 4.6**，这为进一步降低 harness 复杂性提供了动力。从发布博客来看："[Opus 4.6] 更仔细地规划、更持久地执行 Agent 任务、在更大代码库中更可靠地运行，并具有更好的代码审查和调试技能来捕获自己的错误。"它在长上下文检索上也大幅改进。这些都是 harness 原本设计来补充的能力。

### 移除冲刺结构

我首先完全移除了冲刺结构。冲刺结构帮助将工作分解为模型可以连贯处理的块。鉴于 Opus 4.6 的改进，有充分理由相信模型可以原生地处理这项工作而无需这种分解。

我保留了规划器和评估器，因为每个都继续提供明显的价值。没有规划器，生成器会缩小范围：面对原始提示，它会在没有先做规格的情况下开始构建，最终创建的功能丰富的应用不如规划器做的。

移除冲刺结构后，我将评估器移至运行结束时的一次性通过，而非每个冲刺评分。由于模型能力大幅提升，它改变了评估器对某些运行的负载支撑程度——其有用性取决于任务相对于模型可以独自可靠完成的位置。在 4.5 上，这个边界很近：我们的构建处于生成器可以独自做好的边缘，评估器在整个构建中捕获了有意义的问题。在 4.6 上，模型的原始能力增加了，边界向外移动。以前需要评估器检查才能连贯实现的任务，现在通常在生成器独自处理得好的范围内，对于这些边界内的任务，评估器变成了不必要的开销。但对于仍处于生成器能力边缘的构建部分，评估器继续提供真正的提升。

实际意义在于：**评估器不是一个固定的是或否的决策。当任务超出当前模型独自可靠完成的范围时，它才值得成本。**

### 更新 Harness 的结果

为了测试更新后的 harness，我使用了以下提示生成一个数字音频工作站（DAW）：

> *使用 Web Audio API 在浏览器中构建一个功能齐全的 DAW。*

运行仍然漫长且昂贵，约 4 小时，$124 的 Token 成本。

| Agent 和阶段 | 时长 | 成本 |
|---|---|---|
| 规划器 | 4.7 分钟 | $0.46 |
| 构建（第 1 轮） | 2 小时 7 分钟 | $71.08 |
| QA（第 1 轮） | 8.8 分钟 | $3.24 |
| 构建（第 2 轮） | 1 小时 2 分钟 | $36.89 |
| QA（第 2 轮） | 6.8 分钟 | $3.09 |
| 构建（第 3 轮） | 10.9 分钟 | $5.88 |
| QA（第 3 轮） | 9.6 分钟 | $4.06 |
| **总计 V2 Harness** | **3 小时 50 分钟** | **$124.70** |

大多数时间花在构建器上，它在没有 Opus 4.5 所需的冲刺分解的情况下连贯运行了超过两小时。

QA Agent 仍然捕获了真正的差距。在第一轮反馈中，它指出核心 DAW 功能（如音轨拖拽、乐器 UI 面板、效果可视化）仅是显示而没有交互深度。在第二轮反馈中，它再次捕获了多个功能性差距（音频录音仍为存根、音轨边缘拖拽调整大小和分割未实现、效果可视化是数字滑块而非图形化）。

最终应用拥有一个功能音乐制作程序的所有核心组件：一个在浏览器中运行的工作编排视图、混音器和传输控制。此外，我能够完全通过提示创作了一小段歌曲：Agent 设置了节奏和调性，铺下了旋律，构建了鼓音轨，调整了混音器电平，并添加了混响。歌曲创作的核心原语已经具备，Agent 可以使用工具从头到尾自主创建一个简单的制作。

## 下一步

随着模型持续改进，我们大致可以预期它们能够工作更长时间，处理更复杂的任务。在某些情况下，这意味着围绕模型的脚手架会随着时间推移变得不那么重要，开发者可以等待下一个模型并看到某些问题自行解决。另一方面，模型越好，就越有空间开发能够实现超出模型基线能力之复杂任务的 harness。

从这项工作中，有几个经验值得传承：

- **始终用你正在构建的模型做实验**，阅读它在真实问题上的追踪，调优其性能以实现你想要的结果。
- **处理更复杂任务时**，分解任务并将专门化 Agent 应用于问题的每个方面有时会有提升空间。
- **当新模型发布时**，重新审查 harness，剥离不再对性能起支撑作用的部分，添加新部分以实现以前不可能的新能力。

从这项工作中，我的信念是：**有趣的 harness 组合空间不会随着模型改进而缩小。相反，它在移动，而 AI 工程师的有趣工作是不断寻找下一个新颖的组合。**

### 规划器 Agent 生成的示例计划：RetroForge — 2D 复古游戏制作器

**概述**：RetroForge 是一个基于 Web 的创意工作室，用于设计和构建 2D 复古风格电子游戏。它结合了经典 8 位和 16 位游戏美学的怀旧魅力与现代直观的编辑工具——使从业余创作者到独立开发者的任何人都能在不编写传统代码的情况下实现游戏创意。

该平台提供四个集成创意模块：基于图块的**关卡编辑器**（设计游戏世界）、像素艺术**精灵编辑器**（制作视觉资产）、可视化**实体行为系统**（定义游戏逻辑）和即时**可玩测试模式**（实时游戏测试）。通过在各个环节编织 AI 辅助（由 Claude 驱动），RetroForge 加速了创作过程——帮助用户通过自然语言交互生成精灵、设计关卡和配置行为。

**功能模块**：
1. **项目仪表板与管理** — 创建、查看、打开、删除和复制游戏项目
2. **关卡编辑器** — 基于图块的游戏世界设计
3. **精灵编辑器** — 像素艺术视觉资产创作
4. **实体行为系统** — 可视化游戏逻辑定义
5. **可玩测试模式** — 实时游戏测试
6. **AI 辅助功能** — 通过 Claude 生成精灵、设计关卡、配置行为
