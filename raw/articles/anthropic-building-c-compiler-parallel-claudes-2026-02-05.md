# Building a C compiler with a team of parallel Claudes

**Published**: Feb 05, 2026

我们使用 Opus 4.6 和 Agent 团队来构建一个 C 编译器，然后（几乎）放手不管。以下是它教会我们的关于自主软件开发未来的经验。

> - 展望未来

_作者：Nicholas Carlini，Safeguards 团队研究员。_

我一直在尝试一种新的语言模型监督方法，我们称之为"Agent 团队（agent teams）"。

在 Agent 团队中，多个 Claude 实例在没有人类主动干预的情况下，并行地在一个共享代码库上工作。这种方法极大地扩展了 LLM Agent 所能实现的范围。

为了对其进行压力测试，我让 16 个 Agent 从零开始编写一个基于 Rust 的 C 编译器，要求能够编译 Linux 内核。在将近 2,000 个 Claude Code 会话和 20,000 美元的 API 成本之后，Agent 团队产出了一个 10 万行代码的编译器，可以在 x86、ARM 和 RISC-V 上构建 Linux 6.9。

[这个编译器本身是一个有趣的产物](https://github.com/anthropics/claudes-c-compiler)，但在这里我主要关注我在为长期运行的自主 Agent 团队设计 harness（执行框架）方面的经验：如何在没有人类监督的情况下编写让 Agent 保持正轨的测试、如何构建工作以使多个 Agent 能够并行取得进展，以及这种方法在何处达到天花板。

## 启用长期运行的 Claude

现有的 Agent 脚手架（如 Claude Code）需要操作者在线并可用才能共同工作。如果你要求解决一个长期而复杂的问题，模型可能会解决其中的一部分，但最终它会停下来，等待持续的输入——一个问题、状态更新或澄清请求。

为了激发持续的自主进展，我构建了一个将 Claude 置于简单循环中的 harness（如果你见过 Ralph-loop，这看起来很熟悉）。当一个任务完成时，它立即开始下一个任务。_（请在容器中运行此脚本，而不是在你的实际机器上）。_

```bash
#!/bin/bash

while true; do
    COMMIT=$(git rev-parse --short=6 HEAD)
    LOGFILE="agent_logs/agent_${COMMIT}.log"

    claude --dangerously-skip-permissions \
           -p "$(cat AGENT_PROMPT.md)" \
           --model claude-opus-X-Y &> "$LOGFILE"
done
```

在 Agent 提示中，我告诉 Claude 要解决什么问题，并要求它通过将问题分解为小块来解决问题，跟踪它正在做什么，确定下一步做什么，并有效地持续进行直到完美。（关于最后一点，Claude 别无选择——循环永远运行。尽管有一次，我确实看到 Claude 意外地执行了 `pkill -9 bash`，从而杀死了自己并结束了循环。Oops！）

## 并行运行 Claude

并行运行多个实例可以解决单 Agent harness 的两个弱点：

* 一个 Claude Code 会话一次只能做一件事。尤其是随着项目范围的扩大，并行调试多个问题要高效得多。
* 运行多个 Claude Agent 可以实现专业化。当少数 Agent 被指派解决实际问题时，可以调用其他专门的 Agent 来（例如）维护文档、监控代码质量或解决专门的子任务。

我的并行 Claude 实现非常简单。创建一个新的裸 git 仓库，为每个 Agent 启动一个 Docker 容器，将仓库挂载到 `/upstream`。每个 Agent 克隆一个本地副本到 `/workspace`，完成后，从自己的本地容器推送到 upstream。

为了防止两个 Agent 同时尝试解决相同的问题，harness 使用了一个简单的同步算法：

1. Claude 通过在 `current_tasks/` 中写入文本文件来对任务"加锁（lock）"（例如，一个 Agent 可能锁定 `current_tasks/parse_if_statement.txt`，而另一个锁定 `current_tasks/codegen_function_definition.txt`）。如果两个 Agent 尝试认领同一任务，git 的同步机制会强制第二个 Agent 选择另一个任务。
2. Claude 处理任务，然后从 upstream 拉取，合并其他 Agent 的更改，推送自己的更改，并移除锁。合并冲突（merge conflicts）很频繁，但 Claude 足够聪明能够处理。
3. 无限的 Agent 生成循环在新的容器中生成一个新的 Claude Code 会话，循环重复。

这是一个非常早期的研究原型。我还没有实现 Agent 之间通信的其他方法，也没有强制执行管理高层目标的任何流程。我没有使用编排 Agent（orchestration agent）。

相反，我让每个 Claude Agent 自行决定如何行动。在大多数情况下，Claude 会选取"下一个最明显"的问题。当卡在 bug 上时，Claude 通常会维护一个记录失败方法和剩余任务的运行文档。在项目的 [git 仓库](https://github.com/anthropics/claudes-c-compiler) 中，你可以浏览历史并观察它对各种任务加锁的过程。

## 与 Claude Agent 团队编程的经验

脚手架将 Claude 置于循环中，但只有在 Claude 知道如何取得进展时，这个循环才有用。我的大部分精力都用于设计 Claude 周围的环境——测试、环境、反馈——以便它能够在没有我的情况下自行定位方向。以下是我在编排多个 Claude 实例时发现最有帮助的方法。

### 编写极高质量的测试

Claude 会自主地解决我给它的任何问题。因此，任务验证器必须几乎完美，否则 Claude 会解决错误的问题。改进测试 harness 需要找到高质量的编译器测试套件、为开源软件包编写验证器和构建脚本，并观察 Claude 所犯的错误，然后在我识别出这些失败模式时设计新的测试。

例如，在项目接近尾声时，Claude 每次实现新功能时都会频繁地破坏现有功能。为了解决这个问题，我构建了一个持续集成（CI）管道，并实施了更严格的执行机制，使 Claude 能够更好地测试其工作，确保新的提交不会破坏现有代码。

### 设身处地为 Claude 着想

我必须不断提醒自己，我是在为 Claude 而不是为自己编写这个测试 harness，这意味着需要重新思考我关于测试如何传达结果的许多假设。

例如，每个 Agent 都会被放入一个没有上下文的新容器中，并会花费大量时间来确定自己的方向，尤其是在大型项目上。在测试之前，为了帮助 Claude 自助，我包含了维护大量 README 和进度文件的指示，这些文件应该频繁更新当前状态。

我还牢记语言模型存在固有的局限性，在这种情况下需要围绕这些局限性进行设计。这些包括：

* **上下文窗口污染（Context window pollution）**：测试 harness 不应打印数千字节的无用信息。它最多应打印几行输出，并将所有重要信息记录到文件中，以便 Claude 在需要时可以找到。日志文件应易于自动处理：如果有错误，Claude 应写入 ERROR 并将原因放在同一行，以便 grep 可以找到它。预先计算汇总统计数据会有所帮助，这样 Claude 就不必重新计算它们。
* **时间盲症（Time blindness）**：Claude 无法感知时间，如果放任不管，它会花几个小时运行测试而不是取得进展。Harness 不频繁地打印增量进展（以避免污染上下文），并包含一个默认的 `--fast` 选项，运行 1% 或 10% 的随机样本。这个子样本对每个 Agent 是确定性的，但在虚拟机之间是随机的，因此 Claude 仍然覆盖所有文件，但每个 Agent 都可以完美地识别回归。

### 让并行化变得容易

当存在许多不同的失败测试时，并行化很简单：每个 Agent 选择不同的失败测试来处理。当测试套件达到 99% 的通过率后，每个 Agent 致力于让不同的小型开源项目（如 SQLite、Redis、libjpeg、MQuickJS、Lua）能够编译。

但当 Agent 开始编译 Linux 内核时，它们卡住了。与拥有数百个独立测试的测试套件不同，编译 Linux 内核是一个巨大的任务。每个 Agent 都会遇到相同的 bug，修复该 bug，然后覆盖彼此的更改。运行 16 个 Agent 并没有帮助，因为每个都被困在解决相同的任务上。

修复方法是使用 [GCC](https://gcc.gnu.org/) 作为在线的正确编译器预言机（oracle）进行比较。我编写了一个新的测试 harness，随机使用 GCC 编译大部分内核，仅对 Claude 的 C 编译器编译剩余的文件。如果内核正常工作，那么问题就不在 Claude 编译的子集文件中。如果出错了，它可以进一步通过用 GCC 重新编译其中一些文件来细化。这让每个 Agent 能够并行工作，修复不同文件中的不同 bug，直到 Claude 的编译器最终能够编译所有文件。（在这奏效之后，仍然需要应用增量调试（delta debugging）技术来找到一起失败但单独工作正常的文件对。）

### 多 Agent 角色

并行化也实现了专业化。LLM 编写的代码经常重新实现现有功能，因此我指派一个 Agent 合并它发现的任何重复代码。我让另一个负责提高编译器本身的性能，第三个负责输出高效的编译代码。我要求另一个 Agent 从 Rust 开发者的角度批判项目设计，并对项目进行结构性更改以提高整体代码质量，还有一个负责编写文档。

## 压力测试 Agent 团队的极限

这个项目被设计为一个能力基准测试（capability benchmark）。我有兴趣对 LLM 今天_勉强_能做到的极限进行压力测试，以帮助我们为模型未来将可靠实现的目标做好准备。

我一直在使用 C 编译器项目作为整个 Claude 4 模型系列的基准测试。与我之前的项目一样，我首先起草了我想要的东西：从零开始的优化编译器，没有依赖，与 GCC 兼容，能够编译 Linux 内核，设计为支持多个后端。虽然我指定了设计的某些方面（例如它应该有 SSA IR 以启用多个优化通道），但我没有详细说明如何实现。

之前的 Opus 4 模型勉强能够产生一个功能性编译器。Opus 4.5 是第一个跨越阈值的模型，能够产生一个能够通过大型测试套件的功能性编译器，但它仍然无法编译任何真正的大型项目。我的目标是使用 Opus 4.6 再次测试极限。

### 评估（Evaluation）

在两周内进行了将近 2,000 个 Claude Code 会话，Opus 4.6 消耗了 20 亿输入 token 并生成了 1.4 亿输出 token，总成本略低于 20,000 美元。与即使是最昂贵的 Claude Max 计划相比，这都是一个极其昂贵的项目。但这个总额只是我自己生产这个编译器所需成本的一小部分——更不用说整个团队了。

这是一个干净室（clean-room）实现（Claude 在开发过程中完全没有互联网访问）；它仅依赖于 Rust 标准库。这个 10 万行代码的编译器可以在 x86、ARM 和 RISC-V 上构建可启动的 Linux 6.9。它还可以编译 QEMU、FFmpeg、SQLite、PostgreSQL、Redis，并且在大多数编译器测试套件（包括 [GCC torture test suite](https://gcc.gnu.org/onlinedocs/gccint/Torture-Tests.html)）上达到 99% 的通过率。它还通过了开发者的终极试金石测试：它可以编译并运行 Doom。

然而，编译器并非没有限制。这些包括：

* 它缺少引导 Linux 退出实模式（real mode）所需的 16 位 x86 编译器。为此，它调用 GCC（x86_32 和 x86_64 编译器是它自己的）。
* 它没有自己的汇编器（assembler）和链接器（linker）；这些是 Claude 开始自动化的最后部分，仍然有些 bug。演示视频是使用 GCC 汇编器和链接器制作的。
* 编译器成功构建了许多项目，但不是全部。它还不能真正替代真正的编译器。
* 生成的代码效率不高。即使启用了所有优化，其输出代码的效率也不如禁用所有优化的 GCC。
* Rust 代码质量尚可，但远不及专业 Rust 程序员可能产出的质量。

生成的编译器几乎达到了 Opus 能力的极限。我（努力地！）尝试修复上述一些限制，但没有完全成功。新功能和 bug 修复经常破坏现有功能。

作为一个特别具有挑战性的例子，Opus 无法实现启动到 16 位实模式所需的 16 位 x86 代码生成器。虽然编译器可以通过 66/67 操作码前缀输出正确的 16 位 x86 代码，但编译后的输出超过 60KB，远远超出 Linux 强制执行的 32KB 代码限制。相反，Claude 在这里只是作弊并调用 GCC 来完成这个阶段（这只适用于 x86。对于 ARM 或 RISC-V，Claude 的编译器可以完全独立编译。）

[编译器的源代码可在此获取](https://github.com/anthropics/claudes-c-compiler)。下载它，阅读代码，并在你最喜欢的 C 项目上尝试。我始终发现理解语言模型能做什么的最佳方式是将它们推向极限，然后研究它们开始崩溃的地方。在接下来的几天里，如果我想要关注 Claude 继续尝试解决这些限制的进展，你可以跟随 Claude 推送的新更改。

## 展望未来

每一代语言模型都开辟了与它们合作的新方式。早期模型在 IDE 中的 tab 补全很有用。不久之后，模型可以从 docstring 完成整个函数体。Claude Code 的发布将 Agent 带入主流，使开发者能够与 Claude 结对编程。但这些产品都基于这样一个假设：用户定义任务，LLM 运行几秒或几分钟并返回答案，然后用户提供后续指令。

Agent 团队展示了自主实现整个复杂项目的可能性。这使我们作为这些工具的用户，能够在目标上更加雄心勃勃。

我们仍处于早期阶段，完全自主的开发伴随着真正的风险。当人类在开发过程中与 Claude 坐在一起时，他们可以确保一致的质量并实时发现错误。对于自主系统来说，很容易看到测试通过就认为任务完成，而事实往往并非如此。我曾经从事渗透测试工作，利用大公司生产的产品中的漏洞，想到程序员部署他们从未亲自验证过的软件，这是一个真正的担忧。

因此，虽然这个实验让我兴奋，但它也让我感到不安。构建这个编译器是我最近最有趣的事情之一，但我没想到这在 2026 年初就如此接近可能。语言模型和我们用于与它们交互的脚手架的快速进展，为编写大量新代码打开了大门。我期望正面应用将超过负面影响，但我们正在进入一个需要新策略来安全导航的新世界。
